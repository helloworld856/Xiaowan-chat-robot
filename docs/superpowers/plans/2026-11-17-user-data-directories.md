# 用户独立目录实施计划

**目标**　注册后，每个账号都有一个按用户 ID 命名的目录，用于保存个人配置与运行日志。已有账号沿用原目录，升级后资料和 API Key 继续可用。

**方案**　以 MySQL 签发的用户 ID 作为稳定标识。MySQL 继续负责账号、密码哈希、用户名唯一性、聊天历史和摘要。用户目录负责个人资料、个人模型、发送偏好和运行日志。

## 目录结构

```text
backend/user_data/<user_id>/
├── profile.json       # 昵称、系统头像
├── model.json         # 普通用户的模型与 API Key
├── preferences.json   # 发送快捷键
└── logs/
    └── app.log        # 该账号的请求与模型运行诊断，可轮转
```

管理员也拥有自己的资料、偏好和日志目录。管理员的模型设置继续存放在 `backend/settings.json`，Key 继续来自 `backend/.env`。全站启动、MySQL 连接池和匿名请求等日志继续写入 `backend/log_config/app.log`。

## 1. 统一目录与初始化

- [x] 在 `backend/user_data_config.py` 集中生成用户目录及各文件路径。账号 ID 来自已认证的 `User` 或 MySQL 刚写入的记录。复用现有 `backend/user_data/<user_id>/` 路径及 JSON 格式。
- [x] 调整 `backend/app/main.py` 的注册初始化回调。数据库分配 ID 后，准备 `profile.json`、普通账号的空模型配置、默认偏好和日志目录。初始化成功后才提交账户。管理员在启动时走相同的资料目录初始化流程。
- [x] 资料、模型与偏好文件通过同目录临时文件及原子替换写入，同一账号的写操作加锁。在 Ubuntu 上，目录使用 `0700`、个人配置和日志文件使用 `0600`。继续依靠静态资源挂载边界与 Git 忽略规则保护运行数据。
- [x] 验收注册失败可重试、并发同名注册只有一个成功、已有文件字节保持完整。模拟数据库提交结果不明确时，保留可能属于已注册账号的目录。

## 2. 迁移个人偏好及已有账号

- [x] 新增一次性迁移入口 `backend/migrate_user_data.py`，提供 `--dry-run` 和 `--apply`。在启动新版之前扫描现有账号，统计并补齐目录与文件。统计只输出账号数量及迁移结果。
- [x] 从 MySQL 的 `user_preferences` 导入 `send_shortcut`，填入缺失的 `preferences.json`。存在有效个人文件时，保留文件值。发现无法读取的文件时，记录对应账号以便处理。保留原表供回退使用。
- [x] 将 `/settings` 的个人偏好读写切换到 `preferences.json`，保持前端请求和响应格式。保留首次访问时的补建逻辑，支持迁移中断后的重试。
- [x] 验收连续执行迁移两次、已有资料和模型保留、发送快捷键重启后可恢复。账号可以照常登录，聊天仍按账号在 MySQL 中查询。

## 3. 按账号写日志

- [x] 后端认证成功后，为当前请求绑定可信的 `user_id`。将该上下文传入聊天和模型验证所用的工作线程，结束时清理，避免线程被下一位用户复用时误写。
- [x] 在 `backend/log_config/` 按可信的用户上下文选择日志文件。个人日志记录请求结果、回复条数、Token、耗时、保存状态和错误类型。服务器终端继续输出诊断，并为个人事件带上用户 ID。旧的全局日志保留为历史归档。
- [x] 延迟打开个人日志，限制同时保持打开的日志文件数量，沿用约 2 MB 的轮转阈值和三份归档。账号日志写入失败时，将不含请求数据的故障信息记到系统日志，聊天结果仍按原流程返回。
- [x] 并发验证账号 A、B 的聊天和模型测试不会写进彼此目录。另测队列超时、异常退出、线程复用和日志轮转。检查日志中只有运行信息，密钥和聊天原文仍由原有专用存储处理。

- [x] 用隔离 MySQL 和模拟模型验证完整流程，包括新注册、旧资料迁移、普通账号配置 Key、管理员使用 `.env`、两账号并发、聊天历史与个人日志隔离。

- [ ] 如果需要回退，用新版文件中的发送偏好回填保留的 `user_preferences` 表，然后启动旧版。已迁移的用户资料、个人模型及日志目录可继续作为备份。
