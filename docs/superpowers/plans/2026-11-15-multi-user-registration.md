# 小晚多用户注册与独立 LangGraph 实施计划

**目标**　在 `codex/development` 上加入注册和多账号登录，每个账号拥有独立资料和聊天。不同账号可以同时等模型回复，同账号的多设备请求按轮处理。

**架构**　复用 FastAPI、MySQL、LangGraph 和现有 Cookie。每个账号首次发消息时创建自己的 LangGraph、`memorier` 和 `state`，在当前服务运行期间按 `user_id` 复用。每个账号的资料文件位于 `backend/user_data/<user_id>/profile.json`。第一版使用单个 Uvicorn worker，聊天执行使用有并发上限的工作线程。

## 范围与数据生命周期

| 数据 | 存放位置 | 生命周期 |
| --- | --- | --- |
| 账号、密码哈希、角色 | MySQL `users` | 跨重启保留 |
| 昵称、系统头像 | 每个 `user_id` 对应的 `profile.json` | 跨重启保留 |
| 发送快捷键 | MySQL `user_preferences` | 跨重启保留 |
| 登录令牌摘要和身份 | 进程内，按令牌摘要索引 | 8 小时，重启后重新登录 |
| LangGraph、`memorier`、`state`、账号锁 | 进程内 `chat_sessions[user_id]` | 首次聊天按需创建，随服务退出释放 |
| 对话轮次、历史和摘要 | MySQL 按 `user_id` 隔离，运行时按用户缓存 | 服务启动时清空历史和摘要 |
| 模型厂商、名称和接口地址 | 现有 `settings.json` | 全站共享，管理员修改 |

- 每账号一条小晚对话。新账号为普通用户，昵称默认是用户名，默认头像为小猫，继续使用六张系统头像。
- 独立浏览器会话可以同时登录。同一账号在多台设备上共用聊天实例，各设备持有自己的登录令牌。同一浏览器配置下的标签页共享登录 Cookie。
- 每个私有接口用认证中间件提供的 `user_id` 选择数据。用户目录用服务端生成的数字 ID 命名。

## 1. 迁移账户并改造认证

**涉及文件** `backend/database_config/init_mysql.py`、`backend/auth_config/__init__.py`、`backend/app/core/auth.py`、`backend/app/routers/auth.py`、`backend/app/core/app.py`。

- [ ] 分离数据库初始化和日常取连接。初始化创建 `users` 表和唯一用户名索引。用户名接受 3–32 个字母、数字、下划线，查询及唯一性检查统一使用小写形式，显示可以沿用所存拼写。账户 ID 由数据库分配。
- [ ] 做可重跑的管理员导入，把现有 `admin.json` 里的密码哈希和 `profile.json` 里的资料迁到对应账号。验证原密码和资料仍可读取。重复执行时以已迁入的账户和已存在的资料为准；迁移失败返回明确错误，保留旧文件供重试。
- [ ] 登录查询真实账号，令牌映射到 `user_id`。认证中间件为路由提供用户 ID、用户名和角色。`/auth/session` 未登录时返回 `200` 和 `user: null`。退出撤销当前令牌，改密校验本人旧密码并撤销本人全部会话；同账号的登录与改密需要协调，避免改密时发出仍然有效的旧密码会话。
- [ ] 验收管理员迁移可重跑。两个账号分别登录，注销其中一个设备或修改其中一个账号的密码，验证撤销范围。

## 2. 隔离个人资料与设置

**涉及文件** `backend/profile_config.py`、`backend/app/routers/profile.py`、`backend/app/routers/persona.py`、`backend/settings_config.py`、`backend/app/routers/settings.py`、`backend/app/routers/model.py`、`.gitignore`。

- [ ] 将资料存储改成按 `user_id` 读写。资料尚未修改时允许从用户名和默认头像构造返回值，首次保存时创建该用户的资料文件。按账号串行更新，先写同目录临时文件再原子替换，保存失败保留旧文件。将用户资料目录加入 Git 忽略规则，并限制头像 ID 为已有六个选项。
- [ ] `/profile` 和 `/persona` 读取请求账号的资料。`/settings` 为每个账号保存自己的发送快捷键，迁移当前快捷键给管理员。将模型配置与个人偏好分开保存，普通用户读取全站已启用的模型信息。
- [ ] `/model` 和 `/model/test` 从服务端检查管理员角色。应用启动时初始化已保存的模型，移除前端登录时自动调用模型切换接口的做法。
- [ ] 验收 A 改头像、昵称或快捷键不影响 B。同一账号并发提交资料时，磁盘上的 JSON 始终是一份完整记录。普通用户发起模型测试或修改时收到 `403`。

## 3. 为每个账号创建独立的聊天实例

**涉及文件** `backend/app/core/session.py`、`backend/state_config/__init__.py`、`backend/app/routers/chat.py`、`backend/app/routers/history.py`、`backend/graph_config/graph_build.py`、`backend/graph_config/nodes.py`、`backend/memory_config/memory.py`、`backend/memory_config/__init__.py`、`backend/database_config/init_mysql.py`、`backend/agent_config/__init__.py`、`backend/agent_config/agent_factory.py`。

- [ ] 调整聊天表结构。历史记录以 `(user_id, conversation_round)` 为主键，摘要按 `user_id` 唯一保存。将初始化和历史清理移到应用启动时执行一次。`MemoryManager` 构造函数接收 `user_id` 和取连接的工厂，创建时只加载本账号的历史和摘要。每次数据库操作独占借用的连接，事务结束后归还。所有读写、计数和压缩都以实例绑定的 `user_id` 限定范围。
- [ ] 将 `create_graph()` 改成 `create_graph(memorier)`。在编译时把该账号的 `memorier` 绑定到读写历史的节点，移除模块级 `memorier` 的导入和实例化。每个账号编译一次并保留自己的 graph。`create_initial_state()` 每次返回全新的状态，包括内部 `message`、分析结果和消息列表。
- [ ] 在 `chat_sessions[user_id]` 中先建立轻量的账号锁。`/chat` 先异步等待这把锁，再等待全局并发名额。拿到两个名额后的第一次聊天在工作线程里依次创建 `memorier`、graph 和 `state`，成功后一起放入该账号的会话项。初始化失败时保留可重试状态，下一次请求重新创建。注册、登录和 `/history` 可直接使用数据库，只有 `/chat` 创建聊天实例。
- [ ] 同账号的首次并发请求共用一把锁和同一个成功创建的实例。工作线程初始最多同时执行 4 轮并允许调整。账号锁持有至该轮写入结束；客户端断开时仍等待实际任务完成再释放。A 的多个排队请求在账号锁外等待，让 B 有机会使用空闲工作线程。
- [ ] 限制待处理请求。首轮压测以最多 8 个等待名额、最多等待 2 秒为可调起点，时间从收到请求起计算，覆盖账号锁和全局名额的等待。每个账号最多留一个等待请求。全局队列满或等候超时返回 `503`，同账号已有等待请求时返回 `429`。这三种拒绝统一附带错误码 `CHAT_NOT_STARTED`，并且不得执行模型调用或保存消息。
- [ ] 一轮开始时在短锁内取得当前代理组合，并作为本轮运行参数传给节点。分析、回复和摘要全程使用这组代理。管理员切换后，下一轮在原有 graph 上使用新组合。等待模型期间释放全局模型锁和数据库连接。更新摘要与删除被压缩的原文使用同一数据库事务。
- [ ] 为模型的分析、生成和摘要配置网络超时和有限重试。记录排队时间、首次实例初始化时间、各节点耗时、首条回复时间、拒绝与超时次数。先用可控模型替身模拟负载，再用实际配置评估，分别观察中位数和第 95 百分位耗时。
- [ ] 验证注册和登录不创建 graph。A、B 首次聊天后，各自的 graph、`memorier` 和嵌套状态是独立对象。让同账号两次首次请求并发到达，验证只成功创建一次，第二次在等待时限内读取第一次已提交的回复。创建 B 的实例时检查 A 的历史仍在。模拟初始化失败，确认下一次可以正常创建。
- [ ] 阻塞 A 的模型调用时，B 可以先完成。不同账号可以各自保存相同轮次，A 压缩时 B 的历史和摘要保留。让 4 个请求占满工作名额，确认排队超时的请求及时返回，后续不会开始执行。额外验证客户端断开、数据库写入失败和压缩回滚。

## 4. 开放注册并验收整条流程

**涉及文件** `backend/app/routers/auth.py`、`backend/app/core/auth.py`、`frontend/index.html`、`frontend/src/ts/auth.ts`、`frontend/src/ts/api.ts`、`frontend/src/ts/chat.ts`、`frontend/src/ts/main.ts`、`frontend/src/ts/settings.ts`。

- [ ] 在账户和聊天隔离通过后，开放 `POST /auth/register` 与登录页的注册入口。首版使用用户名、密码和确认密码，注册成功返回 `201` 并切回登录页。注册和修改的新密码为 6–15 个字符，现有密码可继续用于登录及旧密码校验。按客户端限制注册和登录尝试，数据库唯一约束确保同时注册同一用户名只会成功一次，重复用户名返回 `409`。
- [ ] 前端根据角色显示模型配置操作，资料、头像、快捷键和聊天回顾从当前账号加载。退出和切换账户时清理页面缓存与未完成请求，复用现有退出确认。
- [ ] 收到 `CHAT_NOT_STARTED` 时，结束等待状态并显示可重试提示，保留原文和用户等待期间已输入的新草稿。对网络超时等执行结果未知的情况，先读取当前历史再决定是否重试。前端现有的回复分条和长度间隔继续适用。
- [ ] 用两个独立浏览器会话完成注册、登录、聊天、资料修改、改密及退出。重启后验证账号和资料可恢复、需要重新登录、历史和摘要为空。在临时 MySQL 数据库验证迁移及并发，避免测试清理用户正在使用的历史。
- [ ] 运行 `python -m unittest discover -s backend/tests -v`、`npm --prefix frontend test`、`npm --prefix frontend run typecheck`、`npm --prefix frontend run build`。将跨用户隔离、同账号串行、注册唯一性和改密撤销范围的检查一并记录。

## 根据压测结果扩容

- 排队耗时高时，先核对服务端资源与模型供应商的容量，再调整并发上限。如果限制来自上游模型服务，增加本地 graph 实例或 worker 不会提高上游吞吐量。
- 排队耗时低、首条回复仍慢时，优先检查分析、生成和摘要各占多少耗时。根据结果考虑优化最慢节点，或另设流式回复任务来改善首响时间。
- 活跃账号增多时测量已创建聊天实例的数量和内存。若空闲实例占用明显，再设计回收策略。只回收没有运行任务或排队请求的实例，并验证重新创建时可恢复该账号的对话轮次、历史和摘要。
- 单进程资源达到上限时，再计划多 worker 或多实例部署。上线前先迁移进程内的登录会话和同账号排队机制，并确保每用户资料文件可由各实例一致地读写。

## 本次验证

- 59 项后端测试和 22 项前端测试通过，TypeScript 检查和生产构建通过。独立 MySQL 8 实例验证了旧表迁移、原账号登录、同时注册同名账号、普通用户权限、两个账号各自保存历史、改密撤销范围和重启后的数据生命周期。
- 真实 LangGraph 配合受控模型验证 A 等待时 B 可完成、同账号串行、限时排队、取消后继续持锁至保存完成，以及摘要事务回滚。在本地浏览器验证注册、聊天、退出确认和跨标签页清理。
- 保留原有从 0 开始的聊天轮次。启动时加载工作流依赖，首次聊天仅编译该账号的 graph。修复 OpenAI 兼容客户端在测试环境中的 Brotli 解码兼容问题后，以当前 DeepSeek 配置并行发送两条合成问候，耗时分别为 2.64 秒和 2.75 秒，总耗时为 2.75 秒。大规模容量仍需按部署环境压测。
